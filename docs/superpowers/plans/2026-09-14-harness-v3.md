# Harness v3: trustworthy acceptance and first use

User-approved scope: bind evidence to source and acceptance definitions; persist attempts;
bound verification to 300 seconds and 10 MiB; explicitly migrate v1/v2 to v3; add safe
initialization, definition-only task maintenance, read-only reports, and bilingual onboarding.

## Constraints and execution

- Python 3.9+ standard library, Git CLI, one writer, local files. No model calls, cloud,
  automatic commits/pushes, release, or license selection.
- Existing checkout is clean and implementation uses `codex/harness-v3` so the result
  stays visible in the user's workspace. Independently owned files can be developed in
  parallel; integration and reviews remain sequential.
- Runtime state, evidence, migration archives, attempts, managed artifacts, reports and
  HANDOFF are fixed snapshot exclusions. Harness code/configuration remain inputs.
- Browser/manual evidence is an attestation at recording time, not independent proof.
- Human adoption validation must be labeled pending until real first-time users try it.

## Tasks

1. Core v3, migration, attempt lifecycle, task add/revise, shared completion audit/report.
   Owner: core implementer. Files: canonical harness.py, existing harness tests and new
   test_harness_v3.py, shipped schema JSON.
2. Bounded subprocess runner with actual timeout/output/interruption tests.

3. Safe init and first-use documentation, complete examples and adoption worksheet.
   Owner: root. Files: harness_init.py, test_init.py, README.md, docs/README.zh-CN.md,
   example scripts/specs, adapters and CI.
4. Integration, adversarial review, regression checks and browser acceptance.

## Shared interfaces

- `harness_runner.run_bounded(argv, workspace, log_path, *, timeout_seconds=300,
  max_output_bytes=10485760) -> RunResult` creates log_path exclusively, streams bounded
  bytes to disk, and returns `returncode`, `reason` (exit/timeout/output_limit/interrupted),
  `bytes_written`, `truncated`. Interruption yields returncode 130 and retains partial log.
  Runner owns termination of the verification process group/tree. No shell execution.
- Core imports `harness_init.initialize(workspace, *, agent=None, dry_run=False,
  source_dir=Path(__file__).parent)` on `init` dispatch; it returns a printable summary.
  The initializer raises ValueError/OSError for conflicts, mapped by core to exit 2.
- `task add --from FILE`: one JSON object with id, title, acceptance; definitions only.
  Acceptance contains id/type/instruction plus command argv or steps, optional positive
  `timeout_seconds` for command checks. Reject state/evidence fields, duplicate IDs.
- `task revise ID --from FILE --note TEXT`: matching ID, pending or in_progress only;
  preserve frozen Git/policy baseline, replace definition explicitly, detach old evidence,
  reset checks to unverified and preserve a revision history. Blocked/done rejected.
- `report ID --format text|json|markdown`: stdout only; common audit with complete.
  JSON includes schema_version, task_id, task_status, ready, checks, issues, next_command.
  Exit 0 means audit ready; 1 means unmet completion gate; 2 configuration/usage error.
  Historical done is displayed explicitly and can never be consumed as an active task.

## Acceptance

- Tests fail before implementing each behavior. Verify stale source, changed contract,
  removed checks, mid-run drift, rerun interruption, missing/tampered evidence.
- Bound real timeout and excessive-output children; retain partial logs; start stays long-lived.
- Preserve v1 migration support and v2 legacy archives; active passed becomes unverified,
  blocked counters and original Git/policy baselines survive.
- Init dry-run/idempotency/conflicts preserve preexisting tasks and host instructions;
  complete command and browser walkthrough in a clean disposable Git repository.
- Run full Python/Node checks, Ruff, doctor and real Chromium acceptance when available.
  Keep Linux/macOS/Windows CI matrix; do not claim remote platforms were run locally.
